# Local Source Corpus

This directory holds third-party material used as authoring reference. It is
**not** committed to git (see `.gitignore`) because:

- Agisoft's PDFs are not ours to redistribute. Each contributor downloads
  their own copy.
- The forum scraping output may include quoted material that must not be
  republished verbatim.
- Cloned third-party repos (e.g. `metashape-scripts`) belong upstream;
  pinned commit shas are recorded in articles, not the source.

## Layout

```
corpus/
├── official/                          # Agisoft user manuals + Python API reference
│   ├── metashape-pro-2_3_en.pdf
│   ├── metashape-standard-2_3_en.pdf
│   ├── metashape-python-api-2_3_1.pdf
│   └── VERSIONS.md                    # downloaded URLs and hashes for reproducibility
├── forum/                             # SMF crawler output (later phases)
│   ├── posts.jsonl
│   └── threads.jsonl
└── scripts/                           # cloned `agisoft-llc/metashape-scripts`
    └── ...
```

## Refreshing the corpus

The official PDFs are versioned with each Metashape release. When a new
version ships:

1. Re-download from <https://www.agisoft.com/downloads/user-manuals/>.
2. Update `official/VERSIONS.md` with the new URLs and SHA-256 hashes.
3. File a release-driven refresh issue so articles
   that pin to a previous version get reviewed.

## Refreshing the forum corpus (incremental update)

The forum corpus is `corpus/forum/printpage-*.html` (full-thread captures,
one file per topic, zero-padded to 5 digits) plus `corpus/forum/index/`
(raw board-index HTML, `parsed/board-*.tsv`, the master `threads.tsv`, and
the tier-A/B/C candidate lists). All of it is gitignored.

Throttle: `agisoft.com/forum` permits crawling `index.php`; use **5 s**
between board-index pages and **10 s** between full printpages. Set a
descriptive `User-Agent` (see `scripts/harvest_board_indexes.sh`).

### Picking up new threads/posts since the last scrape

You do **not** need to re-harvest whole boards. The board index is sorted
newest-first, so newly-created threads appear on **page 1**:

1. **Detect.** Fetch page 1 of each active board
   (`index.php?board=<BID>.0`) and compare against
   `index/parsed/board-<BID>.tsv`: topic IDs absent from the table are new;
   rows whose `last_date` is newer have new posts. Active board IDs are
   `7, 17, 8, 11` (`cut -f2 index/threads.tsv | tail -n +2 | sort | uniq -c`).
   If page 1's *oldest* thread is still newer than your last-scrape date,
   also fetch page 2 (`board=<BID>.15`), etc., until you reach threads that
   are already current.
2. **Merge the index** — parse the page and merge by `topic_id` (update
   existing rows, add new ones); never overwrite a `board-*.tsv` with a
   single page:
   ```bash
   python scripts/parse_board_index.py <page>.html --format tsv > /tmp/new.tsv
   # merge /tmp/new.tsv into index/parsed/board-<BID>.tsv keyed on column 1
   ```
3. **Rebuild** the master table: `python scripts/build_threads_table.py`.
4. **Fetch content** for the new/updated threads (throttled 10 s):
   `index.php?action=printpage;topic=<N>.0` → `printpage-<N>.html`.
5. **Triage / mine:** `python scripts/triage_forum_threads.py` scores
   threads by staff-post count, code blocks, and keyword density; promote
   high-signal threads to insight cards / articles.
6. **Refresh status:** `python scripts/forum_mining_status.py` rewrites
   `insights/MINING_STATUS.md` (a local authoring note).

A **full re-harvest** (`scripts/harvest_board_indexes.sh <BID>` across all
pages) is only needed to refresh `replies`/`last_date` for *older* threads
that got new activity but sit below the pages you fetched — not to pick up
new threads.

## Refreshing the Agisoft Knowledge Base (detecting new / changed articles)

The published KB index (`docs/reference/agisoft-knowledge-base.md`) is
generated by `scripts/gen_kb_reference.py` from two **tracked** files in
`scripts/data/`:

- `kb_master.tsv` — the article inventory
  (`id, folder_id, folder, date_iso, date_raw, title, url`).
- `kb_summaries.tsv` — the hand-written per-article summaries (`id, summary`).

Per-article HTML is cached (gitignored) under
`corpus/freshdesk/articles/<id>.html`. The enumeration source is the portal
**sitemap** (the portal API needs auth; folder pages are JS-rendered). Throttle
every fetch to ~5 s and set a descriptive `User-Agent`.

### 1. Detect new / removed articles (sitemap diff)

```bash
UA="Metashape-Expert-Manual/0.1 (+research, no redistribution)"
curl -s -m30 -A "$UA" https://agisoft.freshdesk.com/support/sitemap.xml > /tmp/kb_sitemap.xml
grep -oE 'solutions/articles/[0-9]+' /tmp/kb_sitemap.xml | grep -oE '[0-9]+' | sort -u > /tmp/kb_live.txt
cut -f1 scripts/data/kb_master.tsv | tail -n +2 | sort -u > /tmp/kb_known.txt

comm -23 /tmp/kb_live.txt /tmp/kb_known.txt   # NEW ids (in sitemap, not in inventory)
comm -13 /tmp/kb_live.txt /tmp/kb_known.txt   # REMOVED ids (in inventory, gone from sitemap)
```

### 2. Detect changed articles

Each article page shows `Modified on: <Day>, DD Mon, YYYY`. Re-fetch known
articles periodically and compare that date against `date_iso` in
`kb_master.tsv`; a newer date means the body changed and its summary may need
rewriting.

### 3. Fetch + extract each new / changed article (throttled ~5 s)

Fetch `https://agisoft.freshdesk.com/support/solutions/articles/<id>` to
`corpus/freshdesk/articles/<id>.html`, then extract:

- **title** — from `<title>… : Helpdesk Portal`
- **modified date** — from `Modified on: …, DD Mon, YYYY`
- **folder** — from the breadcrumb `/support/solutions/folders/<fid>">Name`
- **body** — from the `<article>…</article>` element

### 4. Update the tracked data, regenerate, build

Append/replace the row in `scripts/data/kb_master.tsv`, write a genuine 1-3
sentence summary (read the full body — do not lift the intro) in
`scripts/data/kb_summaries.tsv`, and drop rows for any removed ids. Then:

```bash
./.venv/bin/python scripts/gen_kb_reference.py
./.venv/bin/mkdocs build --strict
```

`scripts/data/` is the canonical source the generator reads; updating
`corpus/freshdesk/` alone has no effect on the published page.

### 5. Cross-reference (the Phase 4 step)

For each new **technique** article, check whether it overlaps an existing
manual article (grep the docs for its key terms); if so, verify our claims
against the KB body and add a cross-reference — fixing any contradiction the
comparison surfaces. Licensing / activation / Agisoft Cloud / Viewer /
release-note / other-language articles have no manual overlap and are
index-only.
